# バッチ生成ガイド

このガイドでは、複数のコントラクト仕様書を効率的に生成するバッチ生成ワークフローの詳細な手順を説明します。

## 概要

バッチ生成ワークフローは2段階のアプローチを使用します：

1. **Stage 1: Skeleton Generation（骨格生成）** - スクリプトを使用してすべてのコントラクトの基本構造を自動生成
2. **Stage 2: AI Enhancement（AI拡張）** - contract-spec-generatorスキルを使用して詳細な説明とエラー追跡を追加

このアプローチにより、以下の利点が得られます：
- ✅ すべてのコントラクトで一貫した構造
- ✅ 初期セットアップの高速化（並列骨格生成）
- ✅ AIが高価値タスク（説明、エラー追跡、modifier情報）に集中
- ✅ 複数のコントラクトの再生成や更新が容易

## 前提条件

このワークフローを実行する前に、以下が必要です：

### 1. Foundry（forge）のインストールと設定

```bash
# Foundryのインストール
curl -L https://foundry.paradigm.xyz | bash
foundryup

# 確認
forge --version
```

### 2. プロジェクト構造

```
contract/
├── src/                          # Solidityソースファイル
│   ├── StablecoinCore.sol
│   ├── StablecoinBank.sol
```

### 3. コントラクトのビルド

スクリプトを実行する前に、forgeでコントラクトをビルドしてABIを生成します：

```bash

```

## Stage 1: Skeleton Generation（骨格生成）

### Step 1: スクリプトの確認

`contract/generate-openapi-specs.js` スクリプトが存在することを確認します。このスクリプトは**高品質な骨格**を生成します：

**自動生成される内容：**
- ✅ **関数パス**（自動生成された説明付き）
  - ロール定数（`_ROLE`）の説明
  - ERC20標準関数の説明
  - Pausable関数の説明
  - AccessControl関数の説明
  - Bank操作の説明
  - Proposal関数（propose*, approve*, execute*）の説明
  - Getter関数（get*, is*, has*, can*）の自動推測説明
- ✅ **正確な型マッピング**（pattern validation + examples）
  - `address` → pattern: `^0x[0-9a-fA-F]{40}$`, example: `0x1234...7890`
  - `bytes4` → pattern: `^0x[0-9a-fA-F]{8}$`, example: `0x12345678`
  - `bytes32` → pattern: `^0x[0-9a-fA-F]{64}$`, example: `0x1234...1234`
  - `uint256` → example: `1000000000000000000`
  - `bool` → example: `true`
- ✅ **書き込み関数への共通エラー自動追加**
  - `InvalidAddress`（addressパラメータがある場合）
  - `AmountZero`（amount/valueパラメータがある場合）
  - `AccessControlUnauthorizedAccount`（ロール関連関数）
  - `BankNotFound`, `BankInactive`（Bank関連関数）
- ✅ **イベントパス**（完全な情報付き）
- ✅ **エラーパス**（完全な情報付き）
- ✅ **基本スキーマ**（ErrorResponse、Eventスキーマ）
- ⚠️ **TODO マーカー**（内部関数エラー追跡のみ - Stage 2で処理）

## Stage 2: AI Enhancement（AI拡張）

### 概要

**Stage 2の焦点：** Stage 1のスクリプトが既に70-80%を処理したため、Stage 2では以下に集中します：

1. **内部関数エラー追跡** - 既存の500レスポンスに内部関数のエラーを追加
2. **500エラーのexamples追加（必須）** - すべてのエラーに対してexamplesセクションを作成
3. **パラメータ説明の追加（必須）** - 型情報だけでなく、意味のある説明を追加（例: `spender` → "トークンの使用を許可するアドレスを指定します"）
4. **Modifier情報** - 関数説明にmodifierの効果を追加
5. **契約特有の説明** - 残っているTODOを詳細な日本語説明に置換

**必須：** 500レスポンスには必ず`examples`セクションを追加すること。各エラーに対して`summary`と`value`を含むnamed exampleを定義する。エラーが9個あれば、examplesにも9個のnamed exampleを定義する。

**重要：** Stage 1で既に処理済みの内容（ERC20説明、型マッピング、共通エラー）は変更しません。

### Step 2: スキルの動作

スキルは以下のステップを自動的に実行します：

1. **高品質な骨格ファイルの読み込み**
   - `docs/contract/StablecoinCore/StablecoinCore.openapi.yaml` を読み込む
   - TODO マーカーを特定（内部関数エラー追跡のみ）
   - 既に自動生成された説明を保持

2. **ソースコードの詳細分析**
   - `contract/src/StablecoinCore.sol` を読み込む
   - 継承チェーンを追跡（`StablecoinHelpers.sol`, `IStablecoinCore.sol`など）
   - **内部関数呼び出しを追跡**（例：`initialize()` → `__Stablecoin_init()` → `_grantRole()`）
   - **内部関数のエラーを特定**（例：`_grantRole()`が投げる`AccessControlBadConfirmation`）
   - modifierの効果を理解（例：`whenNotPaused`, `onlyRole`）

3. **仕様生成ルールの読み込み**
   - `references/spec-prompt.md` から詳細なルールを読み込む
   - フォーマット規則を確認

4. **TODOマーカーの置換と拡張**
   - **内部関数のエラーを追跡**して既存の500レスポンスに追加
     - 例：`initialize()`の500レスポンスに`InvalidInitialization`, `AccessControlBadConfirmation`などを追加
   - **Modifier情報を関数説明に追加**
     - 例：「この関数には `whenNotPaused` modifier が適用されています」
   - **残りのTODOを詳細な日本語説明に置換**
     - 契約特有のロジックを説明

5. **両方のファイルを更新**
   - OpenAPI YAML ファイルを更新
   - Swagger JSON ファイルを更新
   - **既存の自動生成内容（ERC20説明、型パターンなど）は保持**

## トラブルシューティング

### 問題1: スクリプトがABIを見つけられない

**症状:**
```
Error: Cannot find ABI for ContractName
```

**解決策:**
```bash
# forge buildを実行してABIを生成
cd contract
forge build

# out/ディレクトリにABIが生成されたことを確認
ls -la out/StablecoinCore.sol/StablecoinCore.json
```

### 問題2: 内部関数のエラーが追跡されない

**症状:** 500レスポンスに内部関数のエラーが含まれていない

**解決策:**
1. `references/spec-prompt.md` の "Error Tracking" セクションを確認
2. ソースコードで内部関数を手動で確認し、エラーをリスト化
3. スキルに対して明示的に内部関数のエラーを追加するよう指示

```
For StablecoinCore.mint(), also track errors from internal functions:
- _mint(): "ERC20: mint amount exceeds cap"
- _beforeTokenTransfer(): "Pausable: token transfer while paused"
```

### 問題3: YAML/JSON構文エラー

**症状:** 生成されたファイルが無効なYAML/JSON

**解決策:**
1. エラーメッセージを確認
2. インデントを確認（YAMLは2スペース）
3. 特殊文字をエスケープ
4. 複数行文字列は `|` または `>` を使用

### 問題4: フォーマット規則違反

**症状:** バッククォートや接尾辞がある

**解決策:**
1. `references/spec-prompt.md` の "Key Formatting Rules" を再確認
2. スキルに対して明示的にフォーマット規則を再通知

```
Please ensure:
- No backticks around function/event/error names
- No suffixes like "関数", "イベント", "エラー"
```

## ベストプラクティス

### 1. コントラクトの優先順位付け

重要度の高いコントラクトから順に拡張します：

1. **Core contracts**: StablecoinCore, StablecoinBank
2. **Feature contracts**: StablecoinIssuance, StablecoinTransfer
3. **Admin contracts**: StablecoinAdmin, StablecoinRoles
4. **Support contracts**: その他

### 2. バッチでコミット

各コントラクトの拡張後、gitでコミットします：

```bash
git add docs/contract/StablecoinCore/
git commit -m "docs: enhance StablecoinCore specifications with detailed descriptions"
```

### 3. レビューサイクル

3〜5コントラクトごとに、生成された仕様書をレビューします：
- フォーマット規則の一貫性
- 内部関数エラーの追跡精度
- 日本語説明の品質

### 4. ドキュメントサイトでの確認

すべてのコントラクトの拡張が完了したら、Docusaurusサイトで視覚的に確認します：

```bash
cd docs-site
npm run start
```

`http://localhost:3000` で以下を確認：
- すべてのコントラクトが表示される
- サイドバーに関数、イベント、エラーが表示される
- 日本語説明が正しく表示される
- レスポンス例が適切に表示される
